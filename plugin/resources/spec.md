# Спецификация «что строить» — единая форма входа build

Источник: бриф, карточка шаблона, внешний конвейер чтения макета (вне поставки). Цель: для описанного объёма хватает спецификации; пробелы видны и
допускают адресное дочитывание источника. Для короткого багфикса подробный раздел design не нужен — минимум: задача, маршрут,
затронутая область, признаки.

Минимальные поля (design-раздел — для задач, которым он нужен):
- `schemaVersion`, `source` (файл/node-id, ревизия если доступна, время чтения, граница прочитанного)
- `areas[]`: иерархия областей, размеры/constraints, раскладка и адаптация, тексты, ресурсы и ссылки, изображения для сравнения
- `components[]`: library-id, ключ/node-id, кодовое соответствие (namespace+export), варианты; неизвестное — `unresolved`
- `theme`: токены и режимы, привязка к версии профиля/пакета
- `behavior`: взаимодействия, данные, состояния, приёмка — каждое с пометкой `observed | requested | inferred | unknown`
  (статичный макет не доказывает поведение сохранения)
- `facts[]`: таблица признаков (facts.md)
- `conflicts[]`: расхождения с профилем — область, источник решения, итог: `override` (по макету одноразово) ·
  `keep-profile` (сохранить профиль, отклониться от макета) · `update-profile` (сначала профиль, спецификация ссылается на новую
  ревизию); второй редактируемой копии политики нет; изменение макета позже не меняет принятую спецификацию незаметно.
