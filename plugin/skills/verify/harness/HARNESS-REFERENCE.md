# Гейт — справочник (адресное чтение)

> Обычный путь — `HARNESS.md`. Сюда — по id находки, за полями вердикта, exit-кодами, установкой Playwright, не-Vite сборками, фикстурами.

Автоматическая проверка собранного прототипа: контраст текста (APCA — в исходной теме везде, плюс
тёмный проход на дефолт-состоянии свапом темы), битые картинки, пустые image-слоты, разъезд размеров
контролов в ряду, `[object Object]` в текстах, горизонтальный оверфлоу по сетке ширин
(десктоп→мобильная) **в каждом состоянии**, обход всех состояний из `scenarios.manifest.json`, **рамка и
закрепления** (документ не скроллится в заявленной app-рамке; sticky/fixed/`data-pinned`-элементы не
уезжают при прокрутке; высота закреплённого хрома не сжимается при низком окне), плюс static-паттерны
известных ошибок по исходникам.

## Запуск

```bash
# 1) сборка с живыми сценариями (обычный build вырезает dev-переключатель состояний)
VITE_SCENARIOS=1 npm run build
# 2) предпросмотр для гейта — на ВРЕМЕННОМ свободном порту (любом; не занимай порт,
#    который пользователь просил для финального показа)
npx vite preview --port <временный> --strictPort &
# 3) гейт (из папки скилла; <проект> = корень собранного проекта)
node <путь-к-скиллу>/harness/run-gate.mjs http://localhost:<временный> <проект> <проект>/gate-out
# опционально: --fail-on=any|high → exit 1 при находках (для скриптовых/CI-обвязок);
#              --strict → exit 4, если покрытие неполное (см. «Как читать вердикт»)
# 4) после зелёного гейта временный preview можно погасить
```

Результат: `<проект>/gate-out/verdict.json` (формат — `verdict.schema.json` рядом с гейтом) + скриншоты
`full-*.png` по каждому состоянию + сводка в консоли. Гейт сам прогревает сервер перед аудитом (первый
рендер свежеподнятого preview бывает «сырой»).

**Финальный показ пользователю — отдельно от гейта:** удобнее оставить обычный `npm run dev` на порту,
который просил пользователь (в dev сценарии `?scenario=` живые сами по себе + работает HMR); гейтовый
flag-build при этом остаётся честным прод-билдом. Скриншоты гейта (`full-*.png`) полезно просмотреть и
самому — это твои «глаза» на всех состояниях сразу.

## Полный режим и деградация

- **Полный режим** требует Playwright. Гейт ищет его сам, по цепочке: в проверяемом проекте → по пути из
  переменной `GRAVITY_GATE_PLAYWRIGHT` (папка проекта или `node_modules`, где он установлен) → рядом с гейтом →
  в глобальных пакетах npm (`npm root -g`). Достаточно одной установки на машину:
  `npm i -g playwright && playwright install chromium` — дальше каждый новый прототип проверяется без установки
  в проект (хромиум ~130 МБ — спроси пользователя перед установкой). Установка в проект
  (`npm i -D playwright && npx playwright install chromium`) тоже работает и имеет приоритет. В выводе гейта
  строка `· playwright: …` показывает, откуда он взят, если не из проекта.
- **Без Playwright** гейт сам переключается в **static-only**: проверяются только паттерны по исходникам,
  вердикт помечается `mode: "static-only"`, `complete: false`, браузерные ячейки `coverage` — `skipped`.
  Это честный неполный результат, а НЕ «всё чисто».

## Как читать вердикт и что чинить

Три независимых признака — читай в этом порядке:

1. **`valid`** — проверка вообще состоялась. `valid: false` (+ `invalid_reason`) = вердикта нет, это не
   «чисто»: `project_dir_missing` (нет папки проекта) · `manifest_error` (битый `scenarios.manifest.json`
   — сначала почини его) · `page_unreachable` / `blank_document` (сервер не отвечает или пустой документ —
   проверь preview) · `no_visible_content` (документ есть, но ни одного видимого элемента и текста: не
   смонтированное приложение, пустой `#root`) · `ready_selector_not_found` (в манифесте задан `ready`,
   селектор не появился). Exit **3** независимо от флагов.
2. **`complete`** — все запрошенные и применимые проверки выполнены. `coverage.scenarios[<id>]` — матрица
   «сценарий × проверка» (`dom` · `console` · `contrast` · `contrast_dark` · `widths` · `frame` ·
   `screenshot`), каждая ячейка = `"done"` · `{"skipped": <причина>}` · `"out_of_scope"`. Неполноту дают
   только `skipped` (напр. `contrast_dark: {skipped: "no_g_root"}` — тёмный контраст НЕ проверен;
   `unreachable` у сценария). `out_of_scope` — заведомо не в области проверки, полноту не портит:
   тёмный проход только на дефолт-состоянии; на исходно тёмной странице второй замер не делается
   (`dark_pass: "same_as_initial"`, светлая тема не проверялась). `coverage.themes_observed` — темы, как
   их видел гейт по классу `.g-root` (ничего не назначается); `theme_restore: "ok"` — классы темы после
   тёмного прохода восстановлены. `incomplete_reasons` перечисляет пропуски словами. С `--strict`
   неполнота даёт exit **4** (без флага — 0, но в отчёте скажи, что не проверялось).
3. **`summary`** — счётчики находок, **агрегат по всем проверенным состояниям** (ошибка во втором
   сценарии считается так же, как на главном экране); `default_summary` — то же только по
   дефолт-состоянию. `overflow_widths` — число пар «состояние × ширина» с горизонтальным оверфлоу,
   детали в `overflowWidths` по состояниям. `region_overflow` — скролл-контейнеры (overflow-x auto/scroll), чьё содержимое
   шире их самих на опорной ширине: документ при этом не растёт, `overflow_widths` такое не видит; детали в
   `regionOverflow`; контейнер намеренного внутреннего скролла помечается в коде `data-scroll="intended"` (конвенция
   `layout.widget-scroll`) и считается отдельно (`intended_scroll_regions`), не находка. Контраст по APCA — **эвристика
   подозрительного контраста, не полная проверка читаемости** (та зависит от размера, веса и назначения текста): `invisible`
   |Lc|<15 · `poor` <30 · `weak` <45. **Известные ограничения библиотеки** (`known-limitations.json`: селектор · тема · штатный
   токен · основание) помечают находку `known:<id>` только если цвет элемента равен вычисленному штатному токену —
   переопределённый цвет known не получает; счётчик `contrast_*_known` справочный, находка остаётся в списке.
   «0 новых относительно известных» и «0 вообще» — разные утверждения, в отчёт идут оба. **Brand-линия**
   (`brand_text_mismatch`): текст, чей фактический фон равен `--g-color-base-brand` темы, обязан быть цвета
   `--g-color-text-brand-contrast` — сравнение вычисленных значений токенов, не строки `var(...)`; ловит тёмный
   текст на action-кнопке (Lc≈33, для порога `weak` слишком близко к границе). Всё по нулям и `scenario_noop: []` → сборка чиста. С
   `--fail-on` находки дают exit **1** (`any` — любая; `high` — только высокой уверенности:
   invisible-контраст, битые img, `[object Object]`, icon-leak, console, static-high, недостижимые
   сценарии); находки важнее неполноты — при обоих условиях exit 1.
4. **`checks`** — проверки по плану приёмки. `acceptance-plan.json` в корне проекта (или `--plan=<файл>`) пишет build
   (признаки · выбранные конвенции/состояния, формат — `resources/facts.md`); гейт **не доверяет списку build**: пересчитывает
   применимость записей `conventions.json`/`states.json` по признакам сам, существенные признаки перепроверяет по реализации
   (`surface.usesBrandBackground` — по наличию текста на brand-фоне; расхождение → `fact_mismatch`, применимость считается
   по наблюдению), `unknown` → `needs_clarification` (не «не применимо»). Для каждой применимой записи статус её `check.id`
   по `checks.json`: `done` (линия гейта выполнена) · `not-run` с причиной (`needs_human` — ручная приёмка, pass только с
   записью что/где/на какой ревизии проверено; `no_implementation`; `no_scenarios_manifest`; `line_skipped`).
   `plan_mismatch` — что build включил зря / не включил. Нет плана, обязательные `not-run`, `fact_mismatch` или
   `needs_clarification` → `complete: false` с причиной: **ноль находок при обязательных not-run — неполная проверка**,
   не «чисто». Фикстуры-контроли гейта (положительные и отрицательные): `lab/gate-fixtures/run-fixtures.sh` в авторском репо.
- `static` — `files_scanned` (0 = исходников `.ts/.tsx/.js/.jsx` в проекте нет, линия неприменима:
  `skipped_reason: "no_sources"`), `findings[]` — сами находки по исходникам.
- `ready` в манифесте (строка-селектор, напр. `"ready": "#root > *"`) — явный контракт готовности
  приложения вместо эвристики «есть видимое содержимое» (эвристику проходят пустая обёртка с высотой и
  вечный спиннер — при сомнении задай `ready`).
- Находки чини **классами по гайдам registry** (у каждого инварианта есть свой guide-канон: контраст —
  `traps/page-constructor.md` / официальный скилл §Color; оверфлоу — reset/скролл-модели; размеры в ряду —
  `traps/uikit.md`; пустые слоты — `traps/illustrations.md`), а не точечными заплатками под чек.
- `input_icon_inset` — лидирующая иконка в `TextInput` прижата к краю поля (uikit-слот `startContent`
  тесный by design): чинится обёрткой с левым инсетом по размеру контрола (s/m — `spacing-2`, l/xl —
  `spacing-3`) и малым зазором до текста — `traps/icons.md`.
- `scenario_noop` — задекларированный в манифесте сценарий не меняет UI: либо пресеть состояние
  (идиома `FILLED_PRESET` в `templates/app-shell/README.md`), либо убери id из манифеста.
- **Рамка и закрепления** (`frame_*`, `pinned_drift`, `chrome_squeeze`): `frame_leak` — документ
  скроллится, хотя манифест объявил app-рамку (`"frame": {"viewport": true, "minHeight": N}`) —
  чинится вьюпорт-замком (жёсткая высота своей колонки, скролл внутрь; `traps/navigation.md`
  «Модель высоты»); ниже `minHeight` doc-скролл — объявленная политика (`frame_leak_below_floor`),
  не находка. `pinned_drift` — sticky/fixed/`data-pinned`-элемент уехал при прокрутке (сломанный
  sticky или незакреплённый «топбар»). `chrome_squeeze` — закреплённый бар меняет высоту при низком
  окне: во флекс-колонке хрому нужен `flex-shrink: 0` (официальный скилл §Layout, `conventions.json` layout.inner-scroll, вертикальный
  контракт). Элементы, которые обязаны стоять, но не sticky/fixed — помечай атрибутом `data-pinned`.
  `frame_pass: "off"` = рамка не объявлена (frame-замок не проверялся — это не «чисто»).
- Максимум **2 итерации** фикс→повторный гейт на одну находку; не сходится — честно опиши остаток
  пользователю (не подгоняй код под чек и не правь файлы харнеса).

Exit-коды одной строкой: **0** чисто/ниже порога · **1** находки достигли `--fail-on` · **2** ошибка
вызова · **3** невалидный запуск · **4** покрытие неполное при `--strict`.

## Чего гейт НЕ проверяет (зелёный гейт ≠ полная проверка)

- **Доступность за пределами контраста:** клавиатурная навигация/фокус, скрин-ридеры, aria-семантика.
- **Порог контраста — «ловим сломанное», не «доступно»:** |Lc|<15 = невидимый, <30 = плохой; для
  комфортного body-текста APCA рекомендует ~Lc 60+ — зелёный контраст-гейт не сертификат доступности.
- **Фон под текстом** резолвится по цветам слоёв (`backgroundColor` + `::before`); градиент/фото-фон
  гейт не видит — текст на изображениях проверяй глазами (скриншоты `full-*.png`).
- **Готовность приложения** — эвристика «есть видимое содержимое» (элемент с ненулевым боксом и
  вычисленной видимостью; `display:none` / `visibility:hidden` не считаются), не доказательство: пустая
  обёртка с высотой или бесконечный спиннер её проходят. Явный контракт — `ready` в манифесте.
- **Обе темы во всех состояниях:** тёмный проход — только на дефолт-состоянии свапом класса; полный
  замер обеих тем через переключатель приложения не делается (в `coverage` это `out_of_scope`).
- **Контент и смысл:** правдоподобность данных, i18n-длины строк, RTL, копирайт.
- **Интеракции сверх сценариев манифеста:** drag-and-drop, клавиатурные шорткаты, реальная сеть.
- **Границы рамка-линий:** горизонтальные sticky-колонки не проверяются (только вертикальная ось);
  sticky-элемент, не дошедший до точки прилипания, пропускается (уезжает легитимно); «обязан стоять,
  но никак не закреплён» ловится только при явном `data-pinned` или у известного хрома
  (`ActionBar` / `ActionsPanel`); без объявленной в манифесте рамки doc-скролл не считается дефектом.
Это осознанная граница: находки этих классов — владельческий просмотр/vision, не headless-инварианты.

## Не-Vite сборки (Next.js и другие): гейт по URL

Браузерные линии `run-gate.mjs` фреймворк-агностичны — им нужен только URL. Для проекта не на Vite
Vite-команды выше неприменимы: подними прод-сборку проекта своим способом (Next: `npx next build` →
`npx next start -p <порт>`) и запусти `node run-gate.mjs http://localhost:<порт>/<путь> <проект> <проект>/gate-out`.
Ограничения этого режима (честно в отчёте):
- гейт проверяет **один URL за прогон** — многостраничный сайт гоняется по страницам;
- static-линия обходит весь `src/` — в brownfield-репозитории находки могут быть из чужого кода;
  отделяй «моё / было до меня» по `git diff`;
- на сайте с тёмной темой по умолчанию гейт это видит (`themes_observed: ["dark"]`,
  `dark_pass: "same_as_initial"`) и светлую тему не проверяет — напиши «светлая тема на стенде
  не проверялась»;
- `fullPage`-скриншот обрезается на сайтах с внутренним скролл-контейнером (документ не
  скроллится) — снимай высоким вьюпортом (напр. 1280×1400) и скажи об этом в свежем взгляде.
