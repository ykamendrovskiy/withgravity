# build

Корректность компонентов (пакет, версия, API, typecheck) ведёт официальный скилл `gravity-ui`; этот скилл связывает её с
контекстом сервиса. Модель и артефакты — `../../resources/model.md`.

## Вход → маршрут
Прочитай инструкции проекта, зависимости, точку входа; найди `service-profile.json`, `theme/`, `templates/` (или `blocks/` +
`archetypes/` прежнего формата пакета), `catalog/`, `scenarios.manifest.json`, `proposals.json`. Маршрут — по изменяемой части:

| Маршрут | Первое действие | Приёмка |
|---|---|---|
| new-project | контекст сервиса + Template `app-shell` (`../../resources/templates/app-shell/`) | запуск, провайдеры (тост), обе темы |
| new-page | существующие shell/роутинг/тема/соседние экраны; Template из пакета по «когда» | новая страница + сохранность старых; обвязка не дублируется |
| local-fix | воспроизвести, граница изменения, запись использования шаблона | случай + соседнее поведение |
| theme-shell | владельцы провайдеров и токенов; тема по профилю | несколько экранов, обе темы, контраст на бренде |

Вход «что строить» — бриф и/или спецификация `../../resources/spec.md` (из брифа, шаблона или внешнего конвейера). Нет профиля — вопрос на входе (ниже), не молчаливый дефолт.

## Вопросы на входе
Два вызова штатного инструмента вопросов: первый до сборки, второй после таблицы признаков. Каждый вопрос — готовые опции с дефолтом
первой; ответ пользователя записывается в сдачу с пометкой «выбор владельца», дефолт без ответа — «дефолт».

**Вызов 1 — до сборки.**
1. **Профиль сервиса** (задаётся, если `service-profile.json` не найден). Опции: без профиля, по дефолтам Gravity (дефолт) · завести
   профиль интервью (`profile`, затем сборка) · указать путь к профилю или пакету команды.
2. **Тема.** Опции: дефолтная Gravity (дефолт) · из профиля (если есть `themeConfig`) · кастомная.
   Выбрана «кастомная» → **второй вопрос в том же вызове**, опции ровно такие:
   - «готовая тема из проекта рядом: <путь>» — по одной опции на каждую найденную; перед вызовом поищи в соседних папках `theme/*.css`,
     `*.theme.css`, `*.theme.json`, профили с `themeConfig`;
   - «принесу CSS/JSON из Themer» — пользователь кладёт файл экспорта в `theme/` (сделать экспорт: gravity-ui.com/themer);
   - «задам базовый цвет» — свободное поле HEX/rgb; затем генерация по `../../resources/snippets/theme-from-brand-color.md`.
3. **Проверка.** Опции с ценой по времени: полная — гейт + Playwright, обход состояний и ширин в обеих темах, минуты (дефолт, если
   Playwright уже есть; нет — установка ~130 МБ по согласию) · статическая — tsc/build/static, секунды (дефолт без Playwright) ·
   без проверки — в сдаче пометка «не проверено».

**Вызов 2 — после таблицы признаков, один вопрос с мультивыбором.**
4. **Состояния и панель прототипа.** Перечисли применимые записи `states.json`: обязательные (`required`) — «делаю» без выбора;
   исследовательские (partial, варианты пустого, ошибки операций …) — пункты на выбор; последний пункт — «панель прототипа и манифест
   сценариев» (deep link `?scenario=`, переключатель темы, шорткат), отмечен по умолчанию для прототипа/демо и для сборки с ≥ 2
   состояниями. Принятое → `scenarios.manifest.json` + панель по `../../resources/scenarios.md` (через `research-prototype`).

Для new-page и local-fix: п. 3 всегда; п. 1 — если профиля нет и задача про «как принято»; п. 4 — если экран получает состояния.
Автономный/headless прогон — дефолты, перечисленные в сдаче с источником.

Чего не делать: не предлагать свои цвета-пресеты (это выдуманная палитра) · не считать ответ «собирай» ответом на эти вопросы ·
не выбирать за пользователя тему, профиль и режим проверки молча.

## Адресные ресурсы (по мере, не каталогом)
1. Загрузи `gravity-ui` (Skill tool); нет в окружении → остановись и скажи, как установить: `npx skills add gravity-ui/skills`
   (репозиторий gravity-ui/skills; для авто-активации — блок из его README «Activation tip» в AGENTS.md проекта), затем новая сессия. Применимые строки
   `../../resources/errata-official-skill.md`; `@gravity-ui/components` — `../../resources/traps/components.md`.
2. **План приёмки:** заполни признаки по `../../resources/facts.md` (значение · область · основание; action-кнопка = бренд-фон)
   и запиши `acceptance-plan.json` в корень проекта с `entry` (как открыть экран). По признакам выбери записи
   `../../resources/conventions.json` и `../../resources/states.json` (все условия `applies_to.all`; `unknown` → сначала дочитать
   код/измерить, вопрос — только о продуктовом решении). `required` — делается в задаче; исследовательские состояния и панель — вопрос 4 (выше), принятые → `research-prototype`.
3. Запись с `how` → открой сниппет (`../../resources/snippets/`) или грабли по пакету (`../../resources/traps.json`) перед импортом.
4. Профиль — по `../../resources/profile/README.md`. Шаблон — скопировать или импортировать с записью использования
   (`../../resources/templates/card-format.md`), адаптировать видимо. Каталог (`catalog/index.md`) — что уже есть; построил — добавь
   карточку. Конфликт профиля с кодом, от которого зависит сборка, — решить до зависимой работы (сначала что устарело).

## Действие
Версии — установленные (официальный Step 1), не из памяти. `tsc`/`build` → `../verify/SKILL.md` в выбранном режиме; внутри
поручения дефекты уходят в цикл исправления. Порученное — в согласованном объёме; обобщения в правила сервиса — `proposals.json`
(`../../resources/proposals.md`), pending; «так задумано» — классифицируй, не правило. Прочие вопросы по ходу — только о существенной неизвестности (интент; панель прототипа; подбор шаблона при ≥2 подходящих).

## Выход — одна сдача
Ссылка на экран и стартовый сценарий (если заказана панель прототипа — ссылка на dev/scenario-сборку, где панель видна сразу, и шорткат
одной строкой; plain-билд панели не содержит) · что выполнено · настройки с источником (профиль / бриф / дефолт) · взято из пакета / новое ·
качество: новые дефекты / известные ограничения / обязательное непроверенное (из вердикта) · решения владельца · ссылки на
`acceptance-plan.json`, `gate-out/`. Не заставляй читать план, отчёт verify и proposals подряд.

## Не делать
Не выдумывать компоненты/пропы. Не добавлять состояния «на всякий случай» — только применимые по признакам. Не подгонять код под гейт.
Не копировать `app-shell` в существующий проект. Не писать в профиль/шаблоны без поручения.
