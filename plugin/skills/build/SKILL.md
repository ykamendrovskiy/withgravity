# build

Корректность компонентов (пакет, версия, API, typecheck) ведёт официальный скилл `gravity-ui`; этот скилл добавляет контекст сервиса,
план приёмки и сдачу. Модель и артефакты — `../../resources/model.md`.

## 1. Вход и маршрут
Прочитай инструкции проекта, зависимости, точку входа. Найди `service-profile.json`, `theme/`, `templates/` (или `blocks/` + `archetypes/`
прежнего формата пакета), `catalog/`, `scenarios.manifest.json`, `proposals.json`. Вход «что строить» — бриф и/или спецификация
`../../resources/spec.md`. Маршрут выбирай по изменяемой части:

| Маршрут | Первое действие | Приёмка |
|---|---|---|
| new-project | контекст сервиса + Template `app-shell` (`../../resources/templates/app-shell/`) | запуск, провайдеры (тост), обе темы |
| new-page | существующие shell/роутинг/тема/соседние экраны; Template из пакета по «когда» | новая страница + сохранность старых; обвязка не дублируется |
| local-fix | воспроизвести, граница изменения, запись использования шаблона | случай + соседнее поведение |
| theme-shell | владельцы провайдеров и токенов; тема по профилю | несколько экранов, обе темы, контраст на бренде |

## 2. Вопросы на входе
Сначала собери, что уже решено: бриф, предыдущий диалог, профиль (`theme.themeConfig` задаёт тему), существующий проект (его тема и обвязка).
Закрытое не спрашивай — запиши в сдачу как «из брифа» / «из профиля» / «из проекта». Остальное спроси штатным инструментом вопросов,
готовыми опциями, дефолт первой; зависимое уточнение — следующим вызовом после ответа. Ответ пользователя в сдаче — «выбор владельца»,
дефолт без ответа — «дефолт».

**До сборки.**
1. **Профиль сервиса** (нет `service-profile.json`): без профиля, по дефолтам Gravity (дефолт) · завести профиль интервью (`profile`, затем
   сборка; его ответы про тему считаются закрытыми) · указать путь к профилю или пакету команды.
2. **Тема** (new-project и theme-shell; в new-page и local-fix тема проекта сохраняется, если её смена не в задаче): из профиля — первой опцией,
   если профиль её задаёт · дефолтная Gravity · кастомная. Выбрана «кастомная» → следующий вызов, источник: «готовая тема из проекта рядом:
   <путь>» — по одной опции на найденную в рабочей области или названных проектах (искать `theme/*.css`, `*.theme.css|json`, профили с
   `themeConfig`; найденное — кандидат с указанием происхождения) · «принесу CSS/JSON из Themer» (ждём файл в `theme/`; сделать —
   gravity-ui.com/themer; пока файла нет — собирать на дефолтной теме с явной пометкой «временно») · «задам базовый цвет» (свободное поле
   HEX/rgb → `../../resources/snippets/theme-from-brand-color.md`).
3. **Проверка**, с ценой по времени: полная — гейт + Playwright, обход состояний и ширин в обеих темах, минуты (дефолт, если Playwright
   есть; нет — установка ~130 МБ по согласию) · статическая — tsc/build/static, секунды (дефолт без Playwright) · без проверки (в сдаче
   пометка «не проверено»).

**После таблицы признаков, один вопрос с мультивыбором.**
4. **Состояния и панель прототипа:** применимые записи `states.json`; обязательные (`required`) — «делаю» без выбора; исследовательские —
   пункты на выбор; последний пункт «панель прототипа и манифест сценариев» (deep link `?scenario=`, тема, шорткат) отмечен по
   умолчанию для прототипа/демо и для сборки с ≥ 2 состояниями. Принятое → `scenarios.manifest.json` + панель по
   `../../resources/scenarios.md` (через `research-prototype`). В local-fix — только если правка добавляет состояния.

Автономный/headless прогон — дефолты, перечисленные в сдаче как «дефолт». Прочие вопросы по ходу — только о продуктовом решении, которое
нельзя вывести из брифа, профиля или кода.

## 3. Знание — по мере, не каталогом
1. Загрузи `gravity-ui` (Skill tool). Нет в окружении → остановись и скажи, как установить: `npx skills add gravity-ui/skills`, для
   авто-активации — блок «Activation tip» из README gravity-ui/skills в `AGENTS.md` проекта, затем новая сессия.
2. Открой применимые строки `../../resources/errata-official-skill.md`; для `@gravity-ui/components` — `../../resources/traps/components.md`.
3. Профиль применяй по `../../resources/profile/README.md`. Шаблон — скопируй или импортируй с записью использования
   (`../../resources/templates/card-format.md`) и адаптируй видимо. Каталог `catalog/index.md` — что уже есть.
4. Запись конвенции с `how` → открой сниппет (`../../resources/snippets/`) или грабли по пакету (`../../resources/traps.json`) перед
   импортом компонента.
5. Конфликт профиля с кодом, от которого зависит сборка, решай до зависимой работы: сначала установи, что устарело.

## 4. План приёмки
Заполни признаки по `../../resources/facts.md` (значение · область · основание; action-кнопка на бренде = `surface.usesBrandBackground: true`)
и запиши `acceptance-plan.json` в корень проекта с `entry` (как открыть экран). По признакам выбери записи `../../resources/conventions.json`
и `../../resources/states.json`: берётся запись, у которой выполнены все условия `applies_to.all`; `unknown` → сначала дочитай код или
измерь. `required` делается в задаче; исследовательское — по вопросу 4.

## 5. Сборка и проверка
Версии — установленные (официальный Step 1). После `tsc`/`build` выполни `../verify/SKILL.md` в выбранном режиме; внутри поручения
дефекты уходят в цикл исправления. Порученное делай в согласованном объёме; обобщения в правила сервиса записывай в `proposals.json`
(`../../resources/proposals.md`) как pending; «так задумано» классифицируй (исключение / ошибка проверки / решение команды). Построил
новое — добавь карточку в каталог.

## 6. Сдача — одним сообщением
Ссылка на экран и стартовый сценарий (заказана панель — ссылка на dev/scenario-сборку, где панель видна сразу, и шорткат одной
строкой) · что выполнено · настройки с источником (выбор владельца / профиль / бриф / дефолт) · взято из пакета / новое · качество: новые
дефекты, известные ограничения, обязательное непроверенное (из вердикта и `gate-out/evidence.json`) · решения владельца · ссылки на
`acceptance-plan.json`, `gate-out/AUDIT.md`.

## Чего не делать
Не выдумывать компоненты, пропы и палитры. Не решать за пользователя профиль, тему и режим проверки — «собирай» без уточнений их не закрывает, но ранее названное не
переспрашивать. Не добавлять состояния «на всякий случай». Не подгонять код под гейт. Не копировать `app-shell` в существующий проект.
Не писать в профиль и шаблоны без поручения. Не заставлять читать план, отчёт проверки и proposals подряд — сдача одна.
